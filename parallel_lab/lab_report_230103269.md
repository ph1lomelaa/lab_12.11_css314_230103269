Answers:
- BW = 3.34 GB/s, P = 0.166 GFLOP/s, ridge I* = 0.05 FLOP/B. Ridge is very low because pure Python gives few FLOPs, so all 3 variants (I >= 0.125) are on the right side of the ridge -> compute (interpreter) bound, not memory bound.
- Variant 3 with BS* = 64 is fastest (0.0498 GFLOP/s, 30% of roof). W_tile = 96 KB, it is bigger than L1d (64 KB) but fits in L2 (4 MB). BS = 96 and 128 are slower, more loop overhead at row edges and tile does not fit L1 at all.
- Difference between variants is small (1.13x) because in Python the interpreter cost per element (~tens of ns) is much bigger than cache miss cost, so cache blocking helps only a little. Variant 2 was not faster than variant 1 here because it does `c[...] +=` (read + write to shared buffer) in inner loop. max |C3 - C2| = 0, results are equal.

VERIFY_HASH[PHASE4]: 3D866D4FD1B7D992 (P_log=10)

Answers:
- Block static is worst: lambda = 2.40, the last worker gets the heaviest items (work grows like i^2) and others wait for it.
- Cyclic gives lambda = 1.03 because every worker gets light and heavy items. But time is still high, because on M4 4 workers are on P-cores and 6 on E-cores and static split ignores that the E-cores are slower.
- Dynamic queue fixes both: fast cores just take more chunks. C = 1 gives lambda = 1.002 and best time. Lock contention is small here because one item is long (thousands of trig iterations) compared to one lock on mp.Value. C = 512 gives only ~16 chunks for 10 workers, so the last big chunks make tail imbalance (lambda = 1.58).
- C* = 1 on my laptop (C = 8..64 is almost the same). If items were very small C = 1 would lose because of locking, so in general a middle C like 8-64 is safer.
